# DISCO UKRAÏNA Event System

Многоразовая система регистрации и ручного согласования приглашений. Django 5.2 LTS, PostgreSQL 17, Django Admin, Gunicorn и WhiteNoise. Интерфейс регистрации — на украинском.

## Обновлённый кабинет организатора

Админка `/admin/` работает на русском; публичные страницы — на украинском. Вверху кабинета и на экране входа есть переключатель «Тема»: светлая, тёмная или «Как на устройстве». Выбор запоминается в браузере и действует на все страницы админки; в автоматическом режиме оформление следует за системной темой.

- **Обзор:** количество заявок по каждому статусу, быстрые ссылки на страницы и кнопка скачивания общего списка.
- **Заявки:** поиск и фильтры. Большая кнопка **«Скачать список · CSV»** скачивает всю текущую выборку, включая другие страницы результатов. Выделять строки не нужно. Внутри файла — понятные русские заголовки, статусы и время Израиля с UTC offset.
- **Действия над выбранными:** после выбора строк и действия показывается пояснение. Изменение статуса требует отдельного подтверждения с количеством заявок. Экспорт выбранных скачивает только выбранные строки. Массовые изменения записываются в журнал Django Admin.
- **Страницы регистрации:** настройки разделены на название/ссылку, тексты формы, информацию о событии и открытие/закрытие приёма. У каждого поля есть подсказка. Доступны оформление «Велесова ніч 2026» с предоставленной афишей и универсальное оформление без привязки к событию.
- **Как пользоваться:** встроенная инструкция о ссылках, выгрузке файла, значении статусов и кнопках сохранения.

Все четыре статуса — внутренние отметки. Никто не получает письма, SMS или билеты. Можно вообще не менять статусы и работать только с CSV. Пользователь с правом только просмотра может скачать список, но не может менять статусы. Ни списки, ни выгрузка не доступны без авторизации.

Обновление применяет миграции автоматически при запуске контейнера. Существующие контакты, статусы, заметки, тексты и slug сохраняются. Для первой созданной системой страницы выбирается оформление с афишей. Публичные сведения о событии редактируются отдельно от обращения к волонтёрам: дата и время Израиля, название площадки, адрес, краткое описание и раскрывающиеся подробности. Для начальной страницы заполнены предоставленные организатором сведения: 30.10.2026, 19:00, CALLAS TLV, Menachem Begin 37, конкурс костюмов с призом 1000 ₪, бар и скидка 10% в SHO. Упоминание письма накануне относится к отдельной ручной работе организаторов; автоматической отправки нет.

## Возможности

- Кампании с уникальными адресами `/r/<slug>/`, редактируемыми текстами, отключением и необязательным временем закрытия.
- Первая кампания: `/r/zdybanky/`, «Здибанки» — «Велесова ніч», 30 октября 2026 года.
- Заявки: имя, фамилия, телефон, email; заметки доступны только администратору.
- Статусы `PENDING`, `APPROVED`, `REJECTED`, `TICKET_SENT`; ручные переходы без ограничений количества.
- Общий список и фильтры по кампании, статусу и дате; поиск по имени, телефону и email; сортировка по колонкам.
- CSV: примените фильтры и нажмите «Скачать список». Без фильтров скачиваются все кампании. Для отдельных строк используйте действие экспорта выбранных. UTF-8 BOM, защита от формул.
- Нормализация телефонов с регионом IL по умолчанию и поддержкой международного формата. Уникальность email и телефона отдельно внутри кампании, включая ограничения базы.
- Кампании и заявки не удаляются через административный интерфейс. Для закрытия используйте `is_active`.

Система не создаёт и не отправляет билеты, email или SMS. `TICKET_SENT` — только ручная отметка о внешнем действии.

## Подготовка в текущей облачной среде

`./scripts/setup-local.sh` устанавливает зависимости, создаёт локальный `.env` со случайными секретами только при его отсутствии, собирает образ и подготавливает PostgreSQL. Существующий `.env` сохраняется. Затем `docker compose up -d web` запускает приложение. Этот helper предназначен для разработки; production-настройки описаны ниже.

## Локальный запуск с PostgreSQL

Требуются Docker Engine и Docker Compose.

1. Скопируйте `.env.example` в `.env`; замените секрет Django и пароль PostgreSQL. Файл `.env` исключён из Git.
2. Для локального HTTP задайте `DEBUG=1`, `ALLOWED_HOSTS=localhost,127.0.0.1`, очистите `CSRF_TRUSTED_ORIGINS`.
3. Выполните:

```sh
docker compose build
docker compose up -d db
docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py seed_campaign
docker compose run --rm web python manage.py createsuperuser
docker compose up -d web
```

Публичная страница: путь `/r/zdybanky/` на порту 8000. Админка: `/admin/`. Пароля по умолчанию нет. `createsuperuser` безопасно запросит пароль в терминале. Административные записи не создаются автоматически.

В облачных средах, где DNS/сеть недоступны из Docker-сборки, используйте `scripts/build-offline.sh` вместо `docker compose build`. Нужен Python 3.12 с pip на Linux той же архитектуры. Скрипт загружает зафиксированные пакеты через TLS на хосте, затем устанавливает их в образ без сети. Каталог `.wheelhouse` не содержит секретов и исключён из Git, кроме `.gitkeep`.

Повторные `migrate` и `seed_campaign` безопасны: сохранённые тексты и изменённый slug первой кампании не перезаписываются. Если вы вручную создали другую кампанию с `zdybanky` до первого seed, сначала освободите этот slug.

## Разработка без контейнера приложения

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
# Экспортируйте настройки из своего защищённого окружения.
# PostgreSQL обязателен для проверки production-поведения.
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_campaign
.venv/bin/python manage.py runserver 127.0.0.1:8000
```

`USE_SQLITE=1` включает необязательную SQLite только для быстрой локальной разработки. Не используйте её в production: PostgreSQL обеспечивает блокировки при конкурентной отправке формы.

## Тесты

```sh
docker compose run --rm web python manage.py test --verbosity 2
docker compose run --rm web python manage.py makemigrations --check --dry-run
```

Тестовому пользователю PostgreSQL требуется право `CREATEDB`; пользователь локального Compose его имеет. Для внешней production-базы используйте отдельную тестовую базу и учётную запись.

Проверяются: активная страница, успешная регистрация, ошибочные данные, email/телефон-дубли, разные кампании, закрытие/истечение времени, вход и блокировка перебора пароля, создание/редактирование кампаний и slug, все статусы, заметки, поиск/фильтры/сортировка, CSV, отсутствие публичного доступа к данным, CSRF, ограничение частоты запросов, повторяемость seed и отсутствие лимита в 40 человек (55 одобрений и отметок отправки).

## Production

Внешний хостинг, домен, TLS и резервное копирование пока не подключены. Вариант развёртывания: Docker-хост с reverse proxy и PostgreSQL либо управляемая PostgreSQL и контейнерный хостинг.

- `DEBUG=0`, уникальный длинный `DJANGO_SECRET_KEY`, настоящий `ALLOWED_HOSTS` и HTTPS-домен в `CSRF_TRUSTED_ORIGINS`.
- Приложение по умолчанию перенаправляет HTTP на HTTPS; cookie Secure/HttpOnly и HSTS включены. HTTPS завершает reverse proxy. `TRUST_PROXY_SSL=1` включайте только если ваш доверенный proxy удаляет входящий `X-Forwarded-Proto` и устанавливает его сам. Иначе возможна подмена протокола.
- Compose публикует приложение только на loopback; направьте reverse proxy на этот порт. PostgreSQL наружу не публикуется.
- Используйте отдельную учётную запись базы с минимальными правами; не используйте PostgreSQL superuser из локального Compose для публичного production.
- Администратор создаётся вручную. Пять неудачных попыток входа блокируют имя пользователя или IP на час. Для административного сброса: `python manage.py axes_reset`. Доступен встроенный журнал изменений Django Admin.
- Форма ограничивает частоту POST с одного адреса (по умолчанию 100 попыток за 10 минут, настройка `REGISTRATION_RATE_LIMIT`), но не общее количество заявок/одобрений. За reverse proxy реальный адрес клиента нужно передавать только через доверенную конфигурацию; приложение не доверяет произвольному `X-Forwarded-For`. Дополнительно настройте ограничения на proxy. Не записывайте тела форм/пароли в access logs.
- PostgreSQL хранится в Docker volume `postgres_data`. `docker compose down` сохраняет данные; `down -v` уничтожает их. Настройте ежедневные зашифрованные резервные копии, контроль доступа и проверку восстановления. Публикация облачной среды не заменяет резервное копирование Docker volume.
- Проверка `check --deploy` по умолчанию предупреждает об HSTS для поддоменов и preload (W005/W021). Включайте `HSTS_INCLUDE_SUBDOMAINS=1` и `HSTS_PRELOAD=1` только после выбора домена и подтверждения HTTPS для всех его поддоменов; это необязательная политика домена, а не ошибка установки.
- Перед релизом: резервная копия → сборка → `migrate` → перезапуск `web` → проверка страницы и входа. Запускайте `python manage.py check --deploy` с production-настройками.
- CSV содержит персональные данные: храните его с теми же ограничениями доступа, что и базу. Организатор определяет срок хранения и обрабатывает запросы на удаление отдельно; автоматического удаления нет.

Статика входит в Docker-образ и обслуживается WhiteNoise. Афиша события подготовлена из предоставленного PDF и включена в статику в двух размерах JPEG. Пользовательские загрузки изображений, сторонние шрифты и аналитика не используются. Живые процессы и данные Docker не следует считать автоматически перенесёнными в новую облачную задачу. Используйте имеющийся checkout: отдельный Git worktree не требуется.

## Render

`render.yaml` связывает Docker web service и постоянную PostgreSQL в одном регионе. Файл выбирает **платные** планы `starter` (приложение) и `basic-256mb` (база); актуальные цены и доступность необходимо проверить в Render до подтверждения создания ресурсов. Render ещё не подключён, этот файл сам по себе ничего не оплачивает и не публикует. Автоматическое развёртывание при каждом push отключено.

1. В Render откройте **New → Blueprint**, подключите GitHub и выберите этот репозиторий и ветку с приложением.
2. Render найдёт `render.yaml`. Проверьте два ресурса и их стоимость. Подтверждайте создание только после согласия с тарифами.
3. Секрет Django создаётся Render, параметры базы подключаются автоматически. Домен сервиса из `RENDER_EXTERNAL_HOSTNAME` автоматически добавляется в разрешённые хосты и CSRF origins.
4. Дождитесь состояния **Live** у приложения. Откройте адрес сервиса с окончанием `/r/zdybanky/`. Корень сайта пока не содержит публичной страницы.
5. Во вкладке **Shell** web service выполните `python manage.py createsuperuser` и создайте свой логин и пароль. Не пересылайте пароль в чат. После этого откройте `/admin/` на том же домене.
6. Отправьте синтетическую тестовую заявку, проверьте её в админке, изменение статусов и CSV. Только после проверки раздавайте ссылку волонтёрам.

Команда запуска автоматически применяет миграции и создаёт первую кампанию, сохраняя последующие изменения. Gunicorn использует `PORT`, предоставленный хостингом. `/health/` проверяет доступность базы, не раскрывая данные. Render завершает TLS на своём proxy; доверие к `X-Forwarded-Proto` включено для этого размещения. Не подключайте дополнительные недоверенные proxy без проверки настройки.

Не заменяйте PostgreSQL на SQLite: локальная файловая система контейнера Render не предназначена для постоянного хранения заявок. До реального сбора данных проверьте резервное копирование и восстановление на выбранном тарифе.
